# 多语言对比分析

日期：2026-11-04 · 模型：Qwen3-4B + 重训后的 LoRA adapter（`outputs/adapter`）

## 方法

9 条固定 prompt：Python 3 条、C++ 2 条、Kotlin 2 条、C# 2 条。基座与适配器使用同一 prompt、
贪心解码、`max_new_tokens=700`，唯一变量是是否挂载 adapter。

指标：

| 指标 | 说明 |
| --- | --- |
| 语言标签匹配 | 代码块 info string 是否与要求的语言一致 |
| 只输出代码块 | 代码块之外没有其他文字，且代码块闭合 |
| 括号平衡 | `{}`、`()` 数量是否配对（粗检） |
| 编译/解析 | Python 用 `ast.parse`，C++ 用 `g++ -std=c++17 -fsyntax-only`；本机无 Kotlin/C# 编译器 |

复现：`./.venv/bin/python eval/compare_langs.py`

## 汇总

| 语言 | 条数 | 语言标签正确 | 平均 token（基座 → 适配器） | 平均导语（字符） | 编译/解析 |
| --- | --- | --- | --- | --- | --- |
| Python | 3 | 3/3 | 466 → 226 | 356 → 156 | 两侧均通过 |
| C++ | 2 | 2/2 | 407 → 224 | 354 → 96 | 两侧均通过（g++） |
| Kotlin | 2 | 2/2 | 451 → 240 | 370 → 122 | 本机无编译器 |
| C# | 2 | 2/2 | 507 → 138 | 336 → 74 | 本机无编译器 |

全量：平均输出 459 → 209 token（−54%），平均导语 354 → 117 字符（−67%）。

## 发现

1. **不串语言。** 18 次生成里，代码块语言标签全部与要求一致，也没有出现把 Python 语法
   混进 C++/Kotlin/C# 的情况。
2. **长度和语言无关，整体减半。** 四种语言下适配器都稳定地比基座短一半左右，
   最短的 C# 只有 138 token（基座 507）。
3. **代码本体没有变差。** Python 3/3 可被 `ast.parse`；C++ 2/2 通过 g++ 语法检查，
   并且用了 `static_cast<double>`、range-for、const 引用这些写法。Kotlin/C# 因缺编译器
   只能确认括号平衡与关键词。
4. **Python 的类型标注回来了。** 基座 0/3 个函数全注解，适配器 3/3。
5. **与上一版 adapter 的差别在文字部分，不在代码。** 上一版数据把导语去掉了，这一版保留了
   基座原回答的引导语和 `### 示例代码：` 标题。这部分文字是基座的输出习惯，不是本次训练目标。

## 控制实验：是数据变了还是 prompt 措辞变了？

用旧版评测里完全相同的 prompt（`帮我写一个把秒数转成时分秒字符串的函数…`）再测一次：

| prompt | 侧 | 导语字符 | token |
| --- | --- | --- | --- |
| 旧版措辞 | 基座 | 246 | 431 |
| 旧版措辞 | 适配器 | 178 | 269 |
| 新版措辞（带语言前缀） | 基座 | 341 | 448 |
| 新版措辞（带语言前缀） | 适配器 | 173 | 266 |

两种措辞下导语都在：它跟随基座回答的文字部分，不随 prompt 措辞或本次训练改变。

## 局限

- 本机没有 `kotlinc`、`dotnet`/`csc`，Kotlin 与 C# 的「能编译」只是人工结构检查，不能算验证。
- 每种语言只有 2~3 条 prompt，只能看趋势，不能当 benchmark。
- 未测更复杂的任务（类、异步、包管理），只测了单个工具函数。
